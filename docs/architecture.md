# Whale Mind 架构：四层记忆与一次注入

> 这份文档解释「为什么要有四层」以及「每一层负责什么、不负责什么」。
> 所有数字都来自一台真实运行的机器（Windows + AstrBot 4.29 + DeepSeek），不是设计估算。

## 0. 一句话

聊天记录本身不是记忆。**记忆是「从流水里提炼出来、并且能被重新取用」的那部分。**
Whale Mind 把这件事拆成四层，每层只干一件事，层与层之间用文件契约通信。

---

## 1. 四层模型

| 层 | 名字 | 存什么 | 是否进上下文 | 体积代价 |
|---|---|---|---|---|
| L0 | 会话流水 `memory_vault` | 每条消息原文 + 时间 + 来源 | ❌ 永不 | 磁盘 |
| L1 | 提炼记忆 `self_study` | facts / style，一句话一条 | ✅ 每轮按相关性注入 | ~1500 字 |
| L2 | 情感记忆 `emotion_memory` | 带权重与衰减的事件 | ⏳ 待定（影子模式） | ~400 字 |
| L3 | 工作上下文 `context_budget` | 最近若干条对话 | ✅ 每轮全量 | 受预算约束 |

外加两个「按需取用」的旁路：

- **历史检索 `recall_history`**：她主动调工具去翻 L0 的归档（`archive/`）
- **知识卡片 `mnemon`**：跨会话的长期笔记，星图就是它的可视化

### 为什么 L0 不能直接进上下文

实测数据：私聊历史到 241 万字符时，每轮请求约 **25.6 万 token**。
- 全命中时：¥0.003/轮
- 前缀一变（压缩重写、注入位置变动）：¥0.25/轮，差 80 倍
- 而且每 2–3 轮就会发生一次前缀变化

结论：**把「全量历史」当上下文使用，既贵又不可控。** L0 只作为可检索的底账。

### 为什么 L1 要按相关性注入而不是全量

169 条 facts + 49 条 style 全塞进去约 8000 字，而实际每轮只需要 3–5 条相关的。
全量注入会让「记忆」变成噪声，反而稀释人格。

## 2. 数据契约

所有层都以 JSONL 落盘，一行一条，UTF-8，无 BOM。

### L0 `memory_vault/index.jsonl`

```json
{"ts": "2026-11-07 18:12:05", "umo": "qq:FriendMessage:10001",
 "who": "用户", "bot": false, "text": "今天把星图修好了"}
```

- 只追加，不修改
- `umo` 是会话标识（平台:类型:用户），用于隔离不同聊天
- `bot` 区分「她说的」和「他说的」

### L1 `self_study/digest/facts.jsonl` 与 `style.jsonl`

```json
{"time": "2026-11-07 03:00:12", "type": "fact", "text": "用户喜欢雨天",
 "refs": ["2026-11-06.jsonl:233#a1b2c3d4"], "source_raw": "…",
 "source_meta": {"version": "digest-v3", "model": "deepseek-flash",
                 "batch_md5": "ab12cd34", "batch_rows": 24},
 "confidence": 0.9, "weight": 0.9, "hits": 3,
 "aggregate": false, "truncated": false}
```

- `refs` 指回 L0 的具体行（`文件:行号#正文前 8 位 sha1`），**每条记忆都可溯源**
- `aggregate: true` 表示「这条是从多个片段归纳的，没有唯一出处」
- `source_meta.batch_md5` 对应审计文件，可回看模型原始输出

### L2 `emotion_memory/memories.jsonl`

```json
{"memory_id": "…", "text": "…", "original_text": "…",
 "polluted": false, "cluster": "chat", "affect": [0.6, 0.4], "strength": 0.6}
```

- `original_text` 是唯一可信的原文，`text` 可能被「情感滤镜」改写
- **任何检索都必须用 `view="original"`**，否则会读到美化/丑化过的版本

### L3 不进磁盘

工作上下文只存在于内存里，由 `context_budget` 在请求时裁剪。

## 3. 注入预算（每轮总开销）

| 来源 | 上限 | 说明 |
|---|---|---|
| facts | 5 条 | 按 `(0.5·余弦 + 0.5·字面重合) × 权重` 排序 |
| style | 3 条 | 取最近 3 条（风格是恒定的，不需要相关性） |
| 全局记忆 `global_memory` | 20 条 / 2000 字 | 跨会话旁线消息 |
| L2 情感 | 0（未启用） | 影子模式 |
| **合计上限** | **≈ 1500 字** | 超过这个数，记忆就从「帮助」变成「干扰」 |

**注入位置：永远追加到最后一条用户消息的尾部，不碰 system prompt。**
原因见 §4.1。

---

## 4. 三个用钱换来的教训

### 4.1 永远不要往 system prompt 末尾塞「每轮都变」的东西

前缀缓存按字节比对：从第一个不同处开始，后面全部按未命中计费。
把「你记得这些…」（每轮都变）挂在 system prompt 末尾，会导致它之后的整段历史（当时 3.5 万 token）全部失效。

实测对比：

| 注入位置 | 命中率 | 每轮未命中 |
|---|---|---|
| system prompt 末尾 | 6–13% | 35,000–38,000 token |
| 用户消息末尾 | 92.6–93.9% | 630–694 token |

改法：`req.system_prompt` 只放恒定内容，动态内容拼到 `req.prompt` 尾部，并加一句
「以下是系统给你的背景资料，不是用户说的话，不要复述、不要回应这段」。

### 4.2 按「轮数」压缩历史是错的，要按「体积」+「滞回」

AstrBot 自带的 `max_turns` 只看轮数，不看真实字符数。一条长消息就能把上下文顶到 25 万 token。
而它每次触发都会重写历史头部 → 前缀失效 → 全冷。

`context_budget` 的做法：

```
上下文 ≤ 6 万字  → 什么都不做（前缀稳定，缓存持续命中）
上下文 > 6 万字  → 一次裁到 4 万字（留 2 万字缓冲，下次裁剪隔很久）
```

实测（同一套历史）：

| | 裁剪前 | 裁剪后（冷启动） | 裁剪后（稳态） |
|---|---|---|---|
| 上下文 | 46 万字符 | 3.98 万字符 | 3.6 万字符 |
| 未命中 | 248,577 token | 25,005 | 3,451 |
| 命中率 | 3% | 23.8% | 90.5% |
| 单轮成本 | ¥0.25 | ¥0.025 | ¥0.004 |

### 4.3 「提炼」和「原话」必须是两个文件

把用户问句直接存成「记忆」，是这套系统最早犯的错：97 条情感记忆里 96 条与流水重复，其中一条是
`"你还记得我们最早聊的是什么吗"` ——那是提问，不是记忆。

规则：
- L0 只存原话（永不改写）
- L1 只存提炼（每句 ≤ 40 字，必须能独立成立）
- L2 只存「事件 + 感受」（计划中的 v0.2）

## 5. 一次对话的完整数据流

```
用户消息
  │
  ├─ L0 vault  ──► 追加一行（原文，不参与本轮推理）
  │
  ├─ L3 budget ──► 看是否超 6 万字：超了就裁到 4 万，否则原样
  │
  ├─ L1 inject ──► 从 169 条 facts 里挑 5 条 + 3 条 style，拼到消息尾部
  │
  └─ 发给模型 ──► system(恒定 5.4KB) + 历史(≤4 万字) + 本条消息
                     ↑ 前缀稳定 → 缓存命中 ~90%
```

她主动回忆时：

```
她决定调用 recall_history("搬家")
  │
  ├─ 读 live 库（最近几十条）
  ├─ 读 archive/（每天 04:10 落一份，已累积 1964 行）
  └─ 返回片段（命中词 ±60 字，总长 ≤ 1400 字）
```

---

## 6. 设计上明确的「不做」

- ❌ 不做向量数据库（1 万条以内，哈希词袋 + 余弦足够，实测 5000 条约 0.1–0.3 秒）
- ❌ 不做云端同步（记忆是本地的，隐私优先）
- ❌ 不做「自动改写人格」（人格只接受显式的、可回滚的修改）
- ❌ 不把 L0 塞进上下文（见 §4.2 的成本数据）
